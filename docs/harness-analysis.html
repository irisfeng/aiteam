Part 1 · 核心原理

六个子系统，每个含「一句话 + 机制 + 关键代码引用」。设计哲学：一个循环干所有事，差异全靠 RuntimeOpts 表达。

执行内核

① 统一的流式多轮工具循环

聊天 / 干活 / 验收 / 汇总共用同一个 streamRun → llmLoop，差异只靠 RuntimeOpts（preferStrong / tier / toolsOverride）。

  • 每轮 messages.stream 流式出字，delta 经 emit 闭包累加 + WebSocket 全量广播（所谓 SSE 实为 WS fan-out）。
  • stop_reason==tool_use 则执行工具→回推→续跑；否则收口。
  • 运行中插话：每轮把 steerSince 之后的用户新消息注入下一轮迭代。

兼容端点容错四件套

这套 harness 最有特色、也是本次实测修 bug 的重灾区——为了让 DeepSeek 这类第三方 Anthropic 兼容端点稳定干活而塞进循环的四个补丁。

为什么需要它

第三方端点与官方 API 行为有微妙差异：联网工具组合不被接受、thinking 块必须原样回传、网络更抖、对截断文本里的半个 emoji 更严格。任一处不兜底，整段对话就会 400/卡死。

联网工具适配阶梯 — 4xx 自动降档：搜索+抓取→仅搜索→兼容版→停用。engine.ts:1256 你全程看到的 ℹ️ 联网工具适配 即此。
thinking 回传 — echoContent 兼容端点必须保留 thinking/redacted_thinking 块。engine.ts:1210 = 本次修的让 C2 卡死的 400「thinking must be passed back」。
瞬时退避重试 — 网络抖动/5xx/429 退避重试（上限 3 次）。engine.ts:1270
孤立代理项清洗 — stripLoneSurrogates 剔除截断产生的半个 UTF-16 代理项，防 400 hex escape。engine.ts:58

Part 2 · 质量 & 性价比路线图

核心结论：流程正确性扎实，但质量地板是软的——几乎所有不确定路径都倒向「通过」，且产出质量规范大多是默认关闭的可选技能。下面按 影响×成本 排序。

🥇 三个立即该做的 Quick Win

低成本、直接堵住质量地板与降本盲点。

HIGH 影响 LOW 成本 质量

1 验收防放水

问题 校验者没调 submit_verdict 时，代码直接 return {result:"pass"} 并打「按通过处理」——验收最该兜底的失败路径反而判通过。engine.ts:560

改法 无结构化裁决时先强制重试一轮（system 注入「必须且只能调用 submit_verdict」+ tool_choice 强制），仍失败则判 revise 而非 pass，让返工兜住。删掉「按通过处理」那行。

HIGH 影响 LOW 成本 质量

2 产出规范从「可选技能」上移为「常驻约束」

问题 金字塔写作 / 来源标注 / 交付自查表是默认关闭的可选技能，多数用户不开。SHARED_RULES 只讲协作纪律。seed.ts

改法 把「结论先行 + 要点 MECE + 关键事实标来源/检索日期」写进 SHARED_RULES；buildWorkBrief 第 5 点改为强制交付摘要附自查表（验收标准逐条→满足与否→证据位置）。普惠所有任务。

HIGH 影响 MED 成本 降本

3 成本计费分列

问题 把 cache_read（约 1/10 价）和 cache_creation 全当全价 input 计——预算护栏高估成本、提前熔断，且缓存收益不可见。engine.ts:1279

改法 usage 拆成 {input, output, cache_read, cache_creation} 分列；预算用加权 token（cache_read×0.1 + creation×1.25 + input×1 + output×1）。

write_document 落库前做 kind 契约校验

HIGHMED质量+降本 · PPT/数据表

问题 content 不做校验，kind=slides 无 ---、kind=sheet 非合法 CSV 都静默接收，错误要到渲染期才暴露。engine.ts:970

改法 execTool 的 write_document 分支加轻量契约校验，失败作为 tool_result 返回（不落库、引导自纠）：slides 复用 parseSlides 跑一遍要求 ≥2 页且首页有标题；sheet 校验表头存在、各行列数一致；report 仅校验非空。错误给「第 3 行 5 列但表头 4 列」式可执行反馈。

校验者选取去人设化，缺位时降级自查

HIGHMED质量 · 验收

问题 verifier = 名字含「评审」→ 创建者 → others[0]。多数工作区没有「评审」成员，最终落到任意同事做验收，判准漂移。engine.ts:510

改法 验收时临时覆盖 system 为固定「严格校验者」指令（与日常人设解耦，保证可重复）；无其他同事时让作者走自查 rubric 并强制 submit_verdict（至少挡空交付/缺标准项）；audit 记录实际校验者。

分离 cache_read / cache_creation / 纯 input

HIGHMED降本 · 通用

问题 缓存 token 全当全价 input 计：预算高估提前熔断，缓存收益不可见。engine.ts:1279 db.ts usageDaily

改法 usage 扩为 4 列分别累计写入 usage_json；agentDailyStats/usageDaily 同步分列；budgetExhausted 改用加权计费 token；团队/usage 面板展示缓存命中率。

扩大 prompt caching 命中面

MEDMED降本 · 通用

问题 只对 system_prompt 加了 cache_control，且仅官方通道；体量更大的 dynamicCtx 与依赖交付物全文从不缓存。engine.ts:1181

改法 把 dynamicCtx 拆「稳定段」（技能/长期记忆）与「易变段」（看板/文档列表），对稳定段加缓存断点；官方通道下给 messages 稳定前缀加断点，避免多轮重发全价 input。

检索/插件结果按 tool+args 去重缓存

MEDMED降本/稳定 · 通用

问题 只有 MCP_CALLS_PER_RUN 次数上限、无去重，同一查询在多轮里可重复发起并按次计费。engine.ts:1300

改法 loop 内维护 Map<toolName+JSON(args), result>，命中回放且不增计数，tool_result 提示「已检索过，复用结果」；web_fetch 同 URL 去重尤其有效；可选进程级 TTL 缓存跨任务复用热点检索。

裁决与验收落表，建质量度量面板

MEDMED可观测/回归 · 通用

问题 验收结果只打 system 消息，revision_count 无聚合视图，无法回答「一次通过率/哪类返工最多/放水几次」。

改法 新增 verdicts 表（task/verifier/result/reasons/attempt/model）；routes 加 /quality 汇总端点（一次通过率、平均返工、「裁决缺失被兜底」计数）；前端加质量卡片。让「防放水」效果可量化。

04

脆弱点附录

7 路精读识别出的各子系统已知脆弱点 / 风险（折叠展开）。这是上面建议的依据，也是后续迭代的隐患清单。

① 主循环与模型路由 8 项
  • webToolsStage 进程级全局且只升不降，一次 4xx 后永久停用联网到重启，并发下审计行可能刷屏。
  • 瞬时退避在循环内串行阻塞 agent 队列（最坏 2+4+6=12s）；pause_turn 与降档都 iteration--，理论上可被持续 4xx 拖近死循环。
  • supportsAdaptiveThinking 硬编码模型名正则，新模型/改名不挂 thinking，但 echoContent 仍准备回传——能力探测与回传策略不一致。
  • 插话注入只扫 steerSince 时间窗内 10 条，窗口外丢失；所有用户新消息无差别拼一条，长任务里可能重复注入过时插话。
  • echoContent 的过滤是经验白名单而非协议级保证。
  • usage 把 cache token 计入 input 用于预算，护栏高估成本。
  • verifier 选择启发式脆弱（名字含「评审」）；isMock 直接跳过验收。
  • stripLoneSurrogates 只清洗部分回传路径，MCP/图片结果与插话原文未清洗。
② 任务生命周期与验收 7 项
  • fail-open 是质量地板最大漏点：无结构化裁决/isMock/result 非 revise 全倒向 pass，劣质交付静默放行。
  • MAX_REVISIONS 默认 1；达上限转 review，但 checkProject 不区分「验收通过的 review」与「超返工未通过的 review」，质量信号在项目层丢失。
  • 校验者选择靠名字字符串匹配，无评审角色时退化为任意同事，validator 可能不懂该领域。
  • runVerification 自身 streamRun 抛异常会让整个 runTaskWork reject、退回 todo，把「验收崩溃」和「干活崩溃」混为一谈，可能无谓重跑昂贵干活。
  • 交付只取最后一份文档校验，report+slides+sheet 多份组合时其余不经核验。
  • revision_count 持久化了但重启恢复后 attempt 从 0 重来，返工历史不影响新上限。
  • 验收 prompt 只塞最后一份交付物全文，核对前置/多份产出需自己摸 doc_id。
③ 项目 DAG 编排与汇总 8 项
  • 内存调度状态易失：runningTasks/agentQueues 进程内，崩溃后只恢复 doing；停在 todo 的「就绪未跑」任务无后续交付事件触发就永久滞留。
  • MAX_CONCURRENT_WORK=8 写死、无等待队列，被并发挡掉的任务靠一次外部交付事件才重新开工，有饿死风险。
  • onTaskDelivered/checkProject 每次全表扫描找下游，无反向邻接索引，规模化退化。
  • checkProject 用 review 当「已交付」即触发汇总，会把未通过验收的劣质交付物纳入。
  • summary_doc_id 取 createdDocIds 最后一个，Lead 多写/顺序异常会指错；Lead 不写文档时显示「已汇总」却无报告。
  • approve_plan 退回路径弱：拒绝只唤起 Lead，项目停 planned，旧任务悬挂。
  • depsSatisfied 把「依赖任务不存在」当满足，数据损坏时下游被错误提前放行。
  • 无项目级超时/僵死检测，任务卡 doing 永不交付则项目永久 running。
④ 工具系统与外部能力 8 项
  • per-run 计数器是单次 llmLoop 内存变量，任务 revise 重跑会归零，实际花费可远超上限×次数，无任务/项目级累计预算。
  • MCP 连接进程内全局共享且无并发锁，8 并发首次访问同 server 触发 connect 竞态、重复建连泄漏。
  • callCache key 只含工具名+input、不含租户维度，多 channel 下结果可能串数据（隐私）。
  • stdio MCP 以用户配置的 command 启子进程、无白名单，等于任意命令执行面；auth_token 明文存 db。
  • 失败熔断粒度粗：connect 抛错熔断整个 server 5 分钟，瞬时抖动也被熔断、无半开探测。
  • 图片 b64 同步 writeFileSync 落盘阻塞事件循环；assetsDir 无清理/配额，无限增长。
  • 缓存只判 input 相等不判时效，「最新新闻」类 10 分钟内回旧缓存悄悄降时效。
  • MCP inputSchema 原样透传未做大小校验，畸形/超大 schema 进每轮请求放大上下文。
⑤ 状态持久化 / 用量 / 成本护栏 9 项
  • 预算护栏只在 onTaskAssigned 一处检查且只拦自动开工，运行中任务/聊天/验收汇总不受限，无法真正硬切断。
  • 时区不一致：budgetExhausted 用本地零点，账本归因用 Asia/Shanghai，非中国时区窗口错位。
  • 断点恢复是「从头重跑」非检查点续跑，重启重复执行整轮、重复产出与计费，无幂等。
  • token 把 cache_read 计入 input，对计费偏高估，账本无单价/币种维度。
  • 账本与 messages 强耦合，删消息会抹掉历史用量，无独立不可变账本表。
  • 聚合全表扫描 + 应用层 JSON.parse，messages 缺复合索引，量大后 /usage 与每次开工变慢。
  • 并发状态进程内内存，多实例部署（共享库）各算各的互不感知。
  • 真实 client 抛错路径 usage_json 置 null，已消耗 token 丢失不入账。
  • appendMemory 的 FIFO 截断是 O(n²) 反复 join 全文。
⑥ 产出渲染与格式契约 8 项
  • 分页/frontmatter 解析前后端平行双实现（DocsView vs pptx.ts），共享约定不共享代码，任一端改正则即 drift。
  • 几乎零写入校验：声明 slides 却无 ---、声明 sheet 却给散文都原样落库，坏格式到渲染期才暴露。
  • parseSlides 内容分类有损：表格压成 ' · ' 要点、代码/引用/嵌套/加粗被 plain() 抹平，.pptx 与前端富渲染不一致。
  • 数值列判定阈值硬编码 60% 且首列强制当标签，纯数字首列误判、含区间值列被踢出，'1.2万'/'¥1.2k' 解析为 0 静默失真。
  • pptx 版式固定坐标硬编码，内容多了文本框溢出被裁，无自动分页/缩字；首页副标题全角空格拼接易糊。
  • 图片只取 page.images[0]，一页多图丢其余；外链图在 .pptx 无声消失（预览却显示）。
  • isFrontmatter 启发式：正文首页全是「姓名：张三」式冒号行会被误删整页。
  • CSV vs Markdown 表靠是否以 | 开头嗅探，脆弱；revise 重写堆叠多版本文档，验收只看最后一个。
⑦ 提示词、人设与 Agent 设计 7 项
  • SHARED_RULES 在每个 agent 的 system_prompt 编译期内联，改守则需重建 agent 才生效，已存库的是快照、存在版本漂移。
  • 「检索≤3次」「save_memory≤1」全是软约束无运行时强制；web_search 是服务端工具本地无法计数限制。
  • 验收者选择极脆弱，改名/英文名时退化为「随便挑一个」当法官，且未排除验收者自身人设偏见。
  • 技能注入按返回顺序 + 4000 字硬 break，无优先级/相关性筛选，靠后技能静默丢弃，调研任务也被塞金字塔写作法。
  • model_tier 交给 LLM 自评、无校准反馈环，填错档不被发现，light 陷入「做不好→返工→还是 light」浪费循环。
  • brief 前置交付物截断 4000 字、验收 16000、read_document 20000，长链上游信息静默截断无提示。
  • Mock 模式跳过验收，回归测的是「跳过」路径，验收逻辑本身难被自动化测到。
