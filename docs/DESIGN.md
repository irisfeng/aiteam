# AITeam — AI 同事协作工作台（Agent Swarm Workspace）设计文档

> 版本 0.1 · 2026-06 · 目标：打造一款"AI 同事与人类在同一个工作平面协作"的产品。
> 我们借鉴 Helio 的核心工作机制（同频道、同任务、同审计、风险动作等人批准），
> 但不复制 Helio 的功能清单、信息架构或视觉语言；AiTeam 的差异化重点是任务责任链、
> 可观察执行、显式复核与可恢复的人类介入。

## 一、对 Helio 的研究结论

Helio（helio.im）自称 "the AI-native team workspace"。核心信息来自官网、第三方评测
（CodePick、AIChief、TestingCatalog）以及客户端截图，归纳如下：

### 1.1 Helio 的产品形态

| 模块 | 形态 |
|---|---|
| 消息平面 | Slack 式频道 + 私信，**人类与 AI 共用同一个消息平面**（one message plane for humans and AI） |
| AI 同事 | 角色化（工程、招聘、客服、运营…），加入频道、认领任务、保有记忆、留下完整审计轨迹 |
| 任务 | 人与 AI 共用同一个任务看板：AI 自己开票、推进状态、把进度发回频道；**关单是 human-only 操作** |
| 编码会话 | AI 领取编码任务时开隔离沙箱：真实终端/文件系统、可审查 diff、可审计输出 |
| 审批门 | 高风险动作（外发邮件、部署、代签消息）路由给人，一键批准/编辑，类似 PR review |
| 邮件/会议 | 邮件线程同步进频道、AI 起草回复；AI 入会实时转写、决议自动转任务 |
| 多智能体协同 | AI 同事之间**互相分工、互相挑战观点、无需提示即推进任务** |
| 商业化 | 按用量计费（客户端顶部有余额条、加量包入口），demo-first 获客 |

### 1.2 从截图提炼的 UX 细节（值得继承）

- 左侧栏：收件箱 / 任务 / 日历 → 频道 → AI 队友（带头像列表）→ 私信，信息架构非常克制；
- AI 消息带 `AI` 角标，与人类消息同构渲染（头像、姓名、时间戳）；
- AI 回复是结构化长文（标题、列表、表格全量 Markdown），适合"工作产出"而非闲聊气泡；
- 系统事件（建频道、邀请成员）居中弱化显示，构成审计时间线；
- 消息悬浮操作（表情/引用/回复/复制）、"跳到最新"胶囊、@提及、附件计数（+3）；
- 顶部常驻余额/用量条 —— 成本透明是 AI 雇员产品的信任基础。

### 1.3 Helio 的可改进点（我们的机会）

1. **黑盒工作过程**：AI 在"干活中"时用户只能等。→ 我们做**过程透明**：实时流式输出、
   工具调用动作即时可见（"正在创建任务…"）、思考/行动状态指示。
2. **触达成本不透明到消息级**。→ 我们把 token 用量记到每条 AI 消息上，可悬浮查看。
3. **代理间协作不可控**：互相唤起容易雪崩。→ 显式**链深限制 + 单次触发去重**，协作可见、可审计。
4. **配置门槛**：demo-first、不能自助。→ 我们开箱即用：内置角色团队、一条消息即可开工，
   无 API Key 时自动降级 Mock 模式，先体验产品再接入模型。

## 一·B、腾讯 Marvis（马维斯）调研（2026-06 补充）

腾讯应用宝团队 2026-05-20 上线的**操作系统级**个人 AI 助手（Win/Mac/Android，
日送 1000 万 token 免费）。定位与我们不同（个人桌面助手 vs 团队工作台），
但它的多智能体工程与体验设计有多处值得吸收。

### B.1 产品形态

- **1+5 多智能体架构**：主 Agent 是"项目经理"，负责理解需求、拆解任务、调度与汇总；
  5 个专项 Agent 各司其职 —— File（文件搜索/读写/转换）、Computer（系统配置/运维）、
  App（操作本机应用）、Browser（网页接管/抓取）、Search（搜索聚合）。
- **结构化任务派发**：派发不是"传话"，而是携带**完整上下文、历史记忆、依赖关系**的
  结构化描述，让专项 Agent"自包含"地完成子任务，大幅减少来回确认。
- **并行执行 + 自动汇总**：多任务同时派发并行处理；全部完成后主 Agent 汇总产出。
- **执行日志与产出区分离**：过程与结果分区展示。
- **虚拟办公室**：每个 Agent 有工位——干活的坐工位"搬砖"，闲的打盹/闲逛/健身/喝咖啡。
  把"谁在忙什么"变成可感知的空间，状态可视化 + 情感化。
- **定时任务/例行自动化**：每日新闻汇总、签到监控、"每周一自动整理桌面"等。
- **个人知识库**：索引文档，自然语言"记忆碎片"跨文件名/内容/图片元素检索。
- **隐私模式**：本地模型完全离线；效率模式走云端。

### B.2 实测暴露的短板（我们要避开）

慢且"换班"体验割裂（逐截图分析、任务 3-10 分钟）；时间感知幻觉（9:40 设"10 点闹钟"
被设到明天）；高频确认打断流畅度；输出乱码与数据滞后。

### B.3 借鉴清单（按价值排序）

| Marvis 优点 | 映射到 AITeam | 优先级 |
|---|---|---|
| 结构化任务派发（上下文+记忆+**依赖**自包含） | 任务简报结构化：背景/目标/验收标准 + **任务依赖图**——B 依赖 A 时，A 交付后 B 自动开工并注入 A 的交付物 | ⭐⭐⭐ |
| 主 Agent 拆解→并行→**自动汇总** | 「项目模式」收口：Lead 拆解开票，全部子任务交付后自动汇总最终报告（与 agent swarm 调研结论一致，互相印证） | ⭐⭐⭐ |
| 定时任务/例行自动化 | Agent 主动行为：每日站会、定期汇报、监控型任务 | ⭐⭐ |
| 虚拟办公室（状态可视化+情感化） | 低成本等价物：「团队视图」——每个 Agent 显示当前任务/队列/今日完成数/今日 token 消耗 | ⭐⭐ |
| 执行日志/产出区分离 | 已具备（频道时间线 vs 文档库）；可加任务详情页聚合 | ⭐ |
| 时间幻觉教训 | 在动态上下文注入"当前时刻"，杜绝同类错误 | ⭐（顺手修） |
| 隐私模式/本地模型 | 支持自定义 base URL 接本地/代理模型，列为可选项 | 后置 |

## 一·C、《Designing loops with Fable 5》调研（Lance Martin，2026-06 补充）

核心论点：**与其用更重的提示词去"驾驶"模型，不如设计让模型依据环境反馈自我修正的
"循环"**（loops > steering）。文章用两组实验支撑：

1. **目标/评分细则驱动的自纠错循环**：给一个可检验的 rubric（如 Parameter Golf：
   跑基线、做 20 组实验、产物 ≤16MB…），让 Agent 循环"实验→读日志→看分数→决定下一步"，
   由独立的 **grader** 确认全部标准满足后才允许停工。
2. **校验者子代理 > 自我批评**：模型在自己的上下文里自查效果差；
   用**全新上下文的 verifier 子代理**按 rubric 评分，显著更可靠。
3. **记忆的五级阶梯**：失败（记下）→ 调查（弄清为什么）→ **验证**（把诊断变成核实过的
   事实）→ **蒸馏**（升华为通用规则）→ **查阅**（先读规则而不是重新推导）。
   弱模型停在第 1-2 级（一堆失败笔记 + 猜测），强模型完成全程；
   记忆要"更新与去重"，而非无限追加。

### C.1 借鉴清单

| 文章思想 | 映射到 AITeam | 与既有计划的关系 |
|---|---|---|
| rubric 驱动 + grader 把关停工 | 任务「验收标准」字段即 rubric；交付 → **校验者按 rubric 逐条打分**，不达标自动退回返工（有界循环） | 升级"评审返工循环"：从主观评审升级为逐条可检验的验收把关 |
| verifier 全新上下文 | 评审者只拿 rubric + 交付物全文，**不带频道闲聊上下文**，避免被讨论氛围带偏 | 修正当前实现（现在评审者带完整 transcript） |
| 记忆五级阶梯 | 任务后复盘提示词按"失败/原因/核实事实/通用规则"结构化；开工前**先查阅记忆**；记忆做更新去重而非追加 | 升级"任务后复盘"设计 |
| loops > steering | 引擎原则：少在提示词里堆指令，多建"执行→反馈→修正"闭环 | 架构总原则 |

## 一·D、开源明星项目调研与"大道至简"论纲（2026-06 补充）

定位修正（用户指令）：**不照抄 Helio 的形态；核心是数字员工协作完成通用知识工作**
（研究 / 写作 / PPT / 报表…，不限于 coding），**人可干预，也可全自主（闭环）**。

### D.1 明星项目的核心思想

| 项目 | 核心思想 | 对我们的启示 |
|---|---|---|
| **Paperclip**（2026-03 开源，12 天 24K stars，"零人力公司的编排层"） | ①**目标链**：使命→目标→任务逐级携带，Agent 知道"为什么做"；②**心跳**自主运转（定时唤醒查任务队列、上下文跨重启持久、skipWhenIdle）；③**人类 = 董事会**：批准"招聘"、覆盖战略、暂停/终止 Agent，而非逐条微管理；④**预算策略**：阈值告警 + 硬切断自动暂停；⑤不可变审计日志 | 目标链注入任务简报；暂停/终止开关；预算护栏；人类角色定位=治理而非监工 |
| **LangGraph** | interrupt / resume 是人类介入的正确原语：流程可在任意检查点暂停等人、恢复续跑 | 计划审批门 + 运行中插话注入 |
| **AutoGen / AG2** | human-in-the-loop 三档（NEVER / TERMINATE / ALWAYS）——自主度是一个**档位**，不是布尔 | 项目级自主度：全自主 / 计划把关 |
| **CrewAI** | 极简赢得生态：角色+目标+任务，sequential/hierarchical 两种编排就够用 | 验证我们"角色+DAG"的取舍，不做可视化工作流画布 |
| **MetaGPT** | "Code = SOP(Team)"：角色间传递**标准化产物**（PRD/设计/任务单）而非自由聊天 | 验证文档交付物 + rubric 路线 |
| **gpt-researcher / STORM** | planner-executor 并行检索、多视角提问→大纲→成文、全程引用 | 写作/研究类任务的方法论，写入 worker 提示词 |
| **OpenManus / OWL / Suna** | 通用执行底座（浏览器/解释器/MCP 工具流） | M3+ 的执行面扩展方向 |

### D.2 大道至简：唯一核心循环

产品收敛为一个循环，一切功能为它服务，循环外的功能默认不做：

```
目标 → 计划（可把关）→ 并行执行（可插话/可停止）→ 机器验收 → 交付（人关单）
        ↑________________ 记忆复利 / 例行心跳 ________________↓
```

- **人类的三种姿态**（自主度档位）：全自主（auto，闭环跑完只看结果）/
  计划把关（approve_plan，拆解后先批准再开工）/ 随时干预（插话注入 + 停止开关，
  两种档位下都可用）。
- **明确不做**：可视化工作流编排画布、复杂组织架构图、多工作区、邮件/会议集成（暂缓）。
- **模型分工**（choose model wisely）：验收与汇总是质量闭环的下限 → 强制走工作区
  最强通道；worker 按任务类型选；预算护栏防失控。

## 二、产品定义

**一句话**：一个开源的 AI 同事工作台 —— 你和一组角色化的 AI 同事在频道里讨论、
在看板上协作推进任务，高风险动作经过你的审批门，所有过程留痕。

### 2.1 核心对象模型

```
Workspace
 ├─ Agent（AI 同事）: 名字/头像/角色/系统提示词/模型/长期记忆
 ├─ Channel（频道 | 私信）: 成员 = 人类 + 若干 Agent
 ├─ Message: author ∈ {user, agent, system}，支持流式、用量记录
 ├─ Task: 看板四列（待办/进行中/待评审/完成），人与 AI 同构操作
 └─ Approval: Agent 发起的待批动作（pending → approved/rejected）
```

### 2.2 交互协议（多智能体编排规则）

1. **路由**：
   - 私信频道 → 对方 Agent 必然应答；
   - 频道内 `@某Agent` → 精确路由（可多个）；
   - 频道内无提及 → 频道首位 AI 成员应答（默认负责人约定）。
2. **代理链（agent-to-agent）**：Agent 回复中 `@` 另一个 Agent 时会触发对方接力，
   链深默认上限 2（`AGENT_CHAIN_DEPTH`），同一轮内每个 Agent 至多触发一次，防雪崩。
3. **工具面**（Agent 可用的结构化动作，全部留痕广播）：
   - `create_task` / `update_task` —— 与看板直连；指派给 AI 同事即触发对方自动开工；done 关单为 human-only（工具层硬拦截）；
   - `web_search` / `web_fetch` —— Anthropic 服务端工具，真实联网调研；
   - `write_document` / `read_document` —— 正式交付物沉淀到文档库，而非散落聊天流；
   - `request_approval` —— 进入用户收件箱的审批门；
   - `save_memory` —— 写入该 Agent 的长期记忆（跨会话生效）。
4. **任务工作循环（核心）**：任务被指派给 Agent 后（人指派或同事开票分工皆可），它在后台
   自主执行：todo → doing → 多轮"调研/撰写/开衍生任务"工具循环 → `write_document` 交付 →
   系统转 review → 自动唤起评审同事（优先名字含"评审"者，其次开票人）对交付物全文给意见。
   并发护栏：每个 Agent 串行干活（队列化）、全局并发上限 8、运行中任务去重。
4. **上下文构建**：系统提示 = 角色人设（稳定，打 cache 断点）+ 工作区动态上下文
   （队友名册、频道任务快照、个人记忆）；对话以"频道转写"形式提供最近 N 条。
5. **成本与状态**：每条 AI 消息落库 usage（input/output tokens）；
   过程状态（thinking / 使用工具 / responding）通过 WebSocket 实时广播。

### 2.3 模型策略：推荐默认 + 开放接入（BYOM）

原则：**我们推荐模型（默认 Claude），但不锁定** —— 用户可接第三方供应商 API 或本地模型。

**协议选择：统一走 Anthropic Messages 协议，不自写多协议适配层。**
依据：2026 年 Anthropic 协议已是事实上的第二标准 —— DeepSeek、智谱 GLM、Kimi(Moonshot)、
MiniMax 等主流供应商均提供 Anthropic 兼容端点（为兼容 Claude Code 生态）；其余一切
OpenAI 协议的供应商与本地运行时（Ollama / LM Studio / vLLM…）可经 LiteLLM 等网关
一行配置转成 Anthropic 协议。自写 OpenAI 适配层要重做"流式 + 工具循环 + system 块"
三件事的翻译，是持续维护负担，收益却只是省一个网关进程 —— 不做（列为远期可选）。

**接入模型（Provider 抽象）**：
- `providers` 表：`{id, name, base_url, api_key, default_model, is_anthropic_official}`；
  内置一条 Anthropic 官方（base_url 缺省）；用户可增删（设置页/环境变量）。
- Agent 维度：`agent.provider_id + agent.model`，同一工作区可混用——
  例如 PM/校验者用 Claude，闲聊型角色用本地模型。
- 引擎按 provider 构造并缓存 SDK client（`new Anthropic({ baseURL, apiKey })`）。

**能力门控（关键工程点）**：
- `web_search`/`web_fetch` 是 **Anthropic 服务端工具**，仅官方 API 可用 —— 非官方
  provider 自动从工具面剔除（否则 400）；交由提示词告知该同事"无联网调研能力"。
- `thinking: adaptive` 维持按模型名正则门控；`cache_control` 仅官方启用，其余剥离。
- `max_tokens` 随 provider 可配（本地模型上限通常更低）。

**质量分级建议（写进产品推荐文案）**：
- 干活/验收（工具循环可靠性敏感）→ 推荐 `claude-opus-4-8`；
- 聊天/低风险角色 → 任意合格模型；
- 弱模型做 worker 的主要风险是工具调用可靠性与长程一致性，验收循环可以兜一部分底，
  但 verifier 本身必须用强模型（裁决质量决定整个质量闭环）。

**密钥安全**：API key 只存服务端（env / settings），永不下发前端。
无任何 key 时进入 **Mock 模式**：Agent 回复模拟内容，产品全链路可体验。

**DeepSeek 接入速查（2026-06，V4）**：
- Anthropic 兼容端点：`https://api.deepseek.com/anthropic`；
- 模型：默认统一使用 `deepseek-v4-flash`（0731 Agent 增强版）；`deepseek-v4-pro` 仅保留显式回退；旧名 `deepseek-chat`/
  `deepseek-reasoner` 是 V4 Flash 的兼容别名，2026-07-24 起废弃；
- 该端点会把 `claude-opus*` 自动映射为 v4-pro、`claude-sonnet*/haiku*` 映射为 v4-flash；
- 上下文 1M / 最大输出 384K（两档相同）—— 我们默认 max_tokens 16000 可直接用；
- 官方声明其 Anthropic 端点原生支持网页搜索 —— provider 设置中可勾选
  "支持服务端联网工具"开启（运行报错则关闭）。

## 四、技术架构

```
aiteam/
├─ server/   Node 22 + TypeScript
│   ├─ Express(REST) + ws(WebSocket 广播) + better-sqlite3(零运维持久化)
│   └─ agents/engine.ts  多智能体编排：路由→上下文→流式工具循环→链式触发
└─ web/      Vite + React 18 + TypeScript + Tailwind v4
    └─ 单页应用：Sidebar / ChannelView / TasksBoard / Inbox，WS 实时同步
```

- **为何 SQLite**：单文件、零部署依赖、事务足够；消息/任务规模在团队工作台量级绰绰有余。
- **为何自建 WS 而非轮询**：流式 token 广播与 Agent 状态需要 <100ms 推送。
- **为何 REST 写 + WS 读**：写路径简单可重试，读路径实时；客户端无需复杂状态机。

### 4.1 WebSocket 事件协议

| 事件 | 载荷 | 用途 |
|---|---|---|
| `message:new` | Message | 新消息（含流式占位） |
| `message:delta` | {id, delta} | 流式增量 |
| `message:done` | {id, content, usage} | 完成（含用量） |
| `agent:status` | {agentId, channelId, state, detail} | thinking/tool/responding/idle |
| `task:upsert` / `approval:upsert` | 实体 | 看板与收件箱实时刷新 |
| `channel:new` | Channel | 新频道/私信 |

### 4.2 REST 面

`GET /api/bootstrap` · `GET/POST /api/channels/:id/messages` · `POST /api/channels` ·
`POST /api/dms` · `POST /api/agents` · `GET/POST/PATCH /api/tasks` ·
`POST /api/approvals/:id/resolve`

## 六、风险与对策

| 风险 | 对策 |
|---|---|
| 代理互相唤起导致成本失控 | 链深上限 + 轮内去重 + 消息级用量可见 |

| 无 Key 用户流失 | Mock 模式保证全功能可体验 |
